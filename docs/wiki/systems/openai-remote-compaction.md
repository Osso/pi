# OpenAI Remote Compaction

OpenAI remote compaction is implemented as a first-party Pi extension. During `session_before_compact`, the extension handles first-party `openai` provider models using the `openai-responses` API and first-party `openai-codex` / `openai-codex-gc` provider models using the `openai-codex-responses` API.

The extension sends the compacted span to the model's compact endpoint. OpenAI API models use `/responses/compact`; Codex subscription models use the ChatGPT backend `/codex/responses/compact` endpoint with Codex account headers. The request's `instructions` combine Pi's current system prompt with compaction-only continuation guidance and optional instructions supplied through `/compact`. The guidance asks the endpoint to integrate prior context, prefer current state, and collapse repeated or semantically equivalent content instead of reproducing it.

The endpoint returns native OpenAI replacement history, including a `compaction` item with encrypted content. Before storing it, Pi collapses provider-generated `message` rows that are structurally identical except for response-item `id`, retaining the latest copy. Function calls, tool outputs, encrypted compaction items, and messages without provider IDs remain unchanged. Pi stores the resulting native history in the compaction entry's provider-native checkpoint and `details`, while `CompactionEntry.summary` contains only a short synthetic placeholder.

In `/tree`, a plaintext compaction summary opens directly in the editor. An OpenAI-native entry is materialized first through one request using the active model only when its provider/API exactly matches the saved `openai.responses.input` checkpoint; there is no provider/model fallback. Materialization is not persisted. Escape or failure leaves the entry unchanged. Saving the edited native entry atomically replaces the placeholder with plaintext and removes the provider-native checkpoint and OpenAI remote-compaction details while preserving entry identity, tree position, leaf, and token/duration metadata. A newer plaintext compaction is an invalidation barrier, so later remote compactions do not reuse older native replacement history.

Compact input is capped at 400,000 serialized characters. When prior native replacement history and any pinned split-turn opening user fit together, the extension pins the complete native item groups before allocating the remaining budget to newer raw context. If they do not fit together, encrypted `compaction` or `compaction_summary` items remain pinned when they fit beside the opening user while non-encrypted native context is reduced alongside raw context. An encrypted item larger than the available input budget is omitted rather than overflowing the request or cancelling compaction. Native and raw items form separate tool-grouping regions, preventing an orphan native call from splitting a raw call/output pair.

For split-turn compaction, the active turn's opening user message is pinned exactly once inside the same budget before prior non-encrypted native history and newest coherent raw items fill the remaining space. Call/output pairing remains preserved. This rule applies only when the cut is inside the active turn; ordinary multi-turn payload selection is unchanged.

When later context is serialized for an OpenAI Responses model, Pi carries the saved native history on the synthetic compaction-summary message. The shared OpenAI Responses serializer inserts matching native items instead of serializing the synthetic summary text. If a newer plaintext compaction exists, the extension stops at that entry rather than searching past it for older native history.

This keeps Pi's existing session-tree compaction model while preserving OpenAI-native compacted context for OpenAI requests.
